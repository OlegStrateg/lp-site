# LayerPorter — концепция «Аудит → исправленная страница»

Дата: 2026-09-13. Актуализировано после решений о репозитории, переносе по URL и проверке поведения.
Канонический порядок работ: [дорожная карта](LAYERPORTER-ROADMAP.md). Задания: [execution pack](EXECUTION-PACK-2026-09-10.md). Имя этого файла сохранено для совместимости ссылок.
Статус: **PRODUCT DECISION / NOT IMPLEMENTED**. Документ задаёт следующий продуктовый срез; не подтверждает наличие функции в production.
Репозиторий: OlegStrateg/layerporter-site. Реализацию вести от актуального master в отдельной ветке; документационная ветка не является базой для слепого переноса старого кода.

## Решение владельца и рекомендация

Первый рекомендуемый сценарий — **«Проверить страницу»**: единый аудит SEO, видимости в ИИ-поиске, CRO и изображений. Он находит конкретные проблемы, объясняет последствия и показывает ценность исправления. Прямая оптимизация файла остаётся доступной.

Уточнение владельца: НЕ ограничивать диагностику изображениями. Все четыре направления входят в первый агентный пилот. Постепенно расширяется автоматическое исправление, а не искусственно урезается состав аудита. Общий MCP-слой и формат результатов впоследствии переиспользуют сайт и планируемые расширения.

**Обещание продукта: «Проверь страницу и получи улучшенную версию с проверкой того, что работает».**

Путь: репозиторий + выбранная страница ИЛИ публичный URL → единый аудит → 3–5 приоритетных проблем → «Подготовить улучшенную версию» → preview до/после → проверка сценариев → комплект страницы или изменения исходников. Отчёт объясняет ценность, но не является единственным финальным результатом.

Выдача отдельных изображений остаётся быстрым самостоятельным режимом. Улучшение всей страницы — рекомендуемый следующий результат для владельца сайта. Репозиторий подключается один раз; дополнительные настройки запрашиваются только при фактической необходимости.

Первый экран отчёта показывает главные проблемы и выбранное действие; детали — раскрываемые разделы. Тексты, CTA и дизайн меняются по конкретным находкам, а не ради полного редизайна. Сохраняются основной интент, рабочий адрес страницы и релевантная воронка.

V1 — комплексная проверка ОДНОЙ страницы в заявленных категориях. Нельзя называть её полным аудитом сайта. Статический HTML не даёт тех же наблюдений, что реальный браузер: непроверенные категории показываются отдельно.

## Что входит в первый аудит

| Категория | Что проверять | Граница выводов |
| --- | --- | --- |
| Изображения | Доступность, MIME, байты, размеры, кандидаты на другой формат/размер | Экономию подтверждать пробной обработкой, не угадывать процент |
| Разметка изображений | alt, декоративные изображения, img/src, srcset/sizes, width/height, loading | Пустой alt у декоративного изображения допустим; отсутствие любого атрибута не автоматически критическая ошибка |
| Контекст изображений | Соответствие описания видимому изображению и назначению на странице, окружение/подпись | Для смыслового alt нужен просмотр изображения; не выдумывать объекты и не набивать ключевые слова |
| SEO страницы | HTTP, title, description, заголовки, canonical, robots, внутренние ссылки, структурированные данные, соответствие интенту | Без поисковых данных интент и спрос — гипотезы; отсутствие description не доказывает потерю позиций; noindex может быть намеренным |
| Видимость в ИИ-поиске | Доступность содержания, ясные ответы, проверяемые факты и источники, сведения о продукте/авторе, согласованность видимого текста и schema | Это оценка предпосылок, не доказательство цитирования. Реальные упоминания проверять отдельно по записанным запросам/системам/дате. Не обещать попадание в ответы через llms.txt или schema |
| CRO | Понятность предложения, основной CTA, первый экран, трение в загрузке/экспорте/формах, мобильный сценарий, доказательства доверия, релевантный переход в расширение | Без аналитики это наблюдения и гипотезы, не измеренная потеря конверсии; работа кнопки и результата требует реального browser smoke |
| Производительность | Переданный вес изображений, размеры в браузере, загрузка первого экрана, доступные лабораторные измерения | Лабораторные и полевые данные разделять; один запуск не доказывает улучшение INP, CWV или конверсии |
| Метаданные | Существующие сведения об авторе/лицензии; применимость структурированных данных | Не придумывать права, автора и лицензию; не удалять существующие сведения вслепую |

Проверка rendered-размеров, динамических изображений и первого экрана требует браузерного наблюдения. Если его нет, отчёт честно ограничивается статическим HTML. При отсутствии CrUX/GSC показывать «нет данных», а не нули.

Не переименовывать уже индексируемые изображения автоматически ради ключевых слов: изменение URL требует обновления ссылок и отдельной оценки. Для новых файлов можно предлагать короткие описательные имена.

## Как выглядит полезная находка

Каждая карточка содержит:
- конкретную страницу, изображение или элемент;
- наблюдение и доказательство: значение атрибута, статус ответа, байты, скриншот или результат проверки;
- приоритет и понятную причину;
- вероятное последствие отдельно от измеренного результата;
- точное предлагаемое исправление;
- статус: можно подготовить автоматически / нужна проверка человеком / не проверено.

Не использовать вымышленные потери трафика, продаж или «SEO-баллы» без прозрачной методики. Общая статистика с источником может объяснять значимость проблемы, но не становится прогнозом для этой страницы.

Пример измеренной ценности из реального MCP-теста: fashion-reference-960.webp, 960×1329, 68 926 байт → WebP 62 342 байта (−9,55%) или AVIF 39 934 байта (−42,06%). Размеры сохранены, полученные ресурсы полностью декодированы. AVIF заметнее смягчает детали; меньший файл не автоматически лучший выбор. Эти числа не означают соответствующее ускорение всей страницы.

Проверять рекомендации по [Google Image SEO](https://developers.google.com/search/docs/appearance/google-images) и [image license metadata](https://developers.google.com/search/docs/appearance/structured-data/image-license-metadata). Готовый skill направляет агента; сам по себе не выполняет обход, замеры или преобразование файлов.

## Архитектура и результат исправления

Опубликованный @layerporter/image-optimizer-mcp@0.1.0 переиспользуется для детерминированной обработки изображений. Более широкий аудит координирует агент/skill с доступными HTML- и браузерными инструментами. Не объявлять дополнительные проверки возможностями уже выпущенной версии MCP.

Первый пилот — единый агентный сценарий на существующем MCP: один сбор фактов → последовательные профильные проверки → общий отчёт с устранением дублей → выбранные исправления. Общий формат находки включает направление, evidence, приоритет и действие. SEO/CRO/AI-выводы формирует агент по профильным skills; детерминированные проверки и обработку файлов выполняют инструменты. MCP сам по себе не заменяет модель или браузер.

Для следующих расширений переиспользовать договорённый формат данных и модули, а не копировать четыре независимых аудитора. Выносить новый универсальный MCP API только по потребностям проверенного пилота. Публичный веб-аудит произвольных URL потребует отдельного решения по исполнению, лимитам и защите сетевых запросов; не считать локальный stdio сервер готовым hosted API.

## Два входа и честный формат результата

| Вход | Что получает пользователь | Условие готовности |
| --- | --- | --- |
| Репозиторий + страница | Изменения настоящих исходников в отдельной ветке, preview, patch; PR при действующем разрешении | Сборка и ключевые пользовательские сценарии прошли; изменения не затронули лишние страницы |
| HTML + assets / экспорт CMS | Исправленный комплект страницы и инструкция размещения | Локальные пути/ресурсы корректны, проверены адаптивность и заявленные функции |
| Только URL простого лендинга | Восстановленная самостоятельная статическая версия с выбранными улучшениями | До/после проверены заявленные сценарии; все внешние зависимости перечислены и проверены в доступной среде |
| Только URL приложения, магазина или инструмента | Preview-реконструкция, исправленные assets и рекомендации; запрос исходников/CMS для недостающей части | Не выдавать за полноценную замену при отсутствии backend, авторизации, обработки файлов или интеграций |

Не исключать URL-only из продукта. Перед реконструкцией выполнить короткую проверку переносимости: что видно и исполняется в браузере, какие нужны API, формы, учётные записи, внешние assets и окружение. При сложной странице сначала показать, какую часть реально можно подготовить; не тратить большой прогон на заведомо неполный клон.

Репозиторий тоже не гарантирует воспроизводимость: могут отсутствовать env, CMS-контент, backend или права на preview. Запрашивать конкретно недостающее. Секреты не включать в отчёты, архивы и Git.

При переносе на новый origin формы/API могут зависеть от CORS, cookies, разрешённых доменов и настроек провайдера. Успех на localhost не доказывает работу этих интеграций на будущем production-домене. Отдельно фиксировать, что проверено на preview, а что потребует доменной настройки.

«Новая страница» означает новую проверяемую версию. Не менять публичный URL или SEO-интент автоматически. Для статической копии не переносить canonical на чужой домен вслепую; итоговую конфигурацию готовить для согласованного адреса размещения.

## Как минимизируем поломки при переносе и улучшении

1. **До правок:** записать основной путь пользователя, ресурсы и зависимости, текущие ошибки, состояния меню/форм/загрузки и вид на desktop/mobile. Исходные дефекты отделять от внесённых.
2. **При подготовке:** сохранить работающие интерфейсы и контракты. Менять только выбранные элементы; SEO-текст не перекрывает инструмент.
3. **После правок:** выполнить тот же набор сценариев и сравнить ожидаемые результаты. Для видео/изображения — настоящий выходной файл и decode/playback, а не только сообщение «успех».
4. **Визуально:** проверить одинаковые размеры viewport, раскрытые меню, прокрутку и мобильную компоновку. Ожидаемые изменения дизайна согласуются с выбранными исправлениями; точное совпадение пикселей не самоцель.
5. **Технически:** проверить загрузку CSS/fonts/images/JS, console/network, навигацию, форму и ответ доступного тестового backend. Mock не доказывает реальную интеграцию. Не выполнять реальные платежи или отправки сообщений ради smoke без соответствующего разрешения.
6. **На выдаче:** приложить результаты по сценариям, список зависимостей и непроверенных действий. Если ключевой сценарий не работает — статус PARTIAL, с конкретным способом завершить.

Проверка имеет ограниченное покрытие: даже PASS не означает отсутствие всех возможных ошибок. Сравнение до/после ловит регрессии в записанных сценариях; тесты не подгоняются под сломанное поведение.

## Архитектурные границы и поставка

Агент/skills — диагностика, объяснение и выбор изменений. MCP/shared core — проверяемые операции с файлами и структурированные факты. Браузер — состояние и поведение. Git/build — реальные исходники, diff и preview. Сайт и расширения впоследствии используют тот же договорённый формат результатов; не требуют одинакового runtime.

Не встраивать весь AI-аудитор в детерминированный image-optimizer-mcp и не обещать новый API как уже существующий. Сначала доказать пилот и нужные операции, затем версионировать необходимые изменения. Опубликованную npm 0.1.0 не переписывать.

Временные process-local resource URI читаются и превращаются в выходные файлы до окончания процесса. Постоянные download links, хранение, hosted исполнение и пользовательские лимиты проектируются при переходе к веб-продукту.

Пакет результата: отчёт с доказательствами; реестр выбранных изменений; preview; файлы или patch; результаты проверок; инструкция применения и восстановления прежней версии; manifest зависимостей. Исходные файлы не перезаписываются без восстановления.

**Подготовка не равна публикации.** READY FOR REVIEW → VERIFIED IN PREVIEW → READY FOR DEPLOY только при выполнении требований окружения. DEPLOYED VERIFIED — отдельный статус после разрешённого деплоя и production smoke. Если доступен лишь визуальный клон — PREVIEW ONLY.

## Порядок разработки внутри этой линии

| Этап | Результат | Условие перехода |
| --- | --- | --- |
| U1 — репозиторий, одна страница | Все четыре направления аудита + выбранные исправления + рабочая страница в preview | Реальный путь пользователя до/после, валидный файл, проверенные ссылки/разметка, ограниченный diff |
| U2 — URL без исходников | Проверка переносимости; полный статический комплект для простого лендинга; честный PARTIAL для сложного инструмента | Две контрольные страницы: переносимая и зависимая от backend; отсутствуют ложные заявления о полноте |
| U3 — повторяемое использование | Общий формат evidence/change/output, установка по инструкции, понятная выдача файлов | Другой чистый запуск повторяет результат без ручных скрытых шагов; фактическая совместимость клиента указана |
| U4 — сайт и расширение | Один выбранный интерфейс над проверенным сценарием | Определены runtime, стоимость, доступы, хранение; проверен полный путь до результата |
| Позже | Обход многих страниц, CMS-адаптеры, применение/деплой, расширенный мониторинг | Есть спрос по результатам пилота и отдельные критерии надёжности |

Не строить универсальный конструктор сайтов до U1. Не ждать U2–U4, чтобы закончить и оценить полезную работу с репозиторием. На каждом этапе ограниченный набор сценариев, исправление обнаруженных дефектов и остановка после приёмки.

## Приёмка U1

На одной реальной странице LayerPorter:
1. Сверить актуальную ветку, существующий функционал и оригинальный путь пользователя; записать baseline.
2. Получить единый отчёт SEO + AI-поиск + CRO + изображения, со статусом покрытия каждого направления, доказательствами и приоритетами без дублей.
3. Подготовить выбранные полезные изменения страницы; при наличии — исправление изображения и разметки. Не создавать дефекты ради теста.
4. Для оптимизации получить файлы через MCP Resources, проверить MIME/размеры/полный decode, показать изменение байтов и визуальное сравнение.
5. Проверить сборку, ссылки, mobile/desktop и основной сценарий на изменённой странице. Для общего шаблона проверить ещё одну затронутую страницу.
6. Выдать исправленную страницу в preview и пригодный к применению patch с точной базой; сохранять URL, работавшие функции и сведения о правах.
7. Приложить SHA/diff, доказательства и ограничения. CI/HTTP 200 не заменяют функциональную проверку. Без deploy не ставить production VERIFIED.

Метрики: начат аудит → завершён аудит → подготовлена версия → сценарии прошли → скачан комплект / применён patch. Дополнительно: время до полезного результата, стоимость запуска, доля PARTIAL, причины непереносимости. Вес, скорость, трафик, цитирования и конверсия измеряются раздельно.
