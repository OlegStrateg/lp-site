# LayerPorter — каноническая дорожная карта

Статус: **каноническая стратегия проекта**.
Дата фиксации: 2026-09-08.
Master tracker: GitHub Issue #153.

Эта дорожная карта определяет порядок работ по сайту, SEO, AI-поиску, CRO, локализациям, расширениям и общему функциональному ядру. Техническая дорожная карта редактора `_internal/EDITOR-PLATFORM-ROADMAP.md` остаётся подчинённой продуктовой дорожной картой и не должна противоречить этому документу.

## 1. Каноническая продуктовая модель

### Расширения

Расширение — **узкий продукт под один понятный поисковый интент**.

Примеры:
- Pinterest Downloader → скачать медиа с Pinterest;
- Picture Converter → скачать/конвертировать изображение;
- будущий Extract Audio from Video → извлечь аудио из видео.

Правило: не смешивать в позиционировании расширения десятки функций ради охвата. Основной запрос, обещание и первый пользовательский сценарий должны быть сфокусированы.

### Сайт

Сайт — **общая многофункциональная платформа LayerPorter** с переиспользуемым ядром.

Универсальные функции сайта должны одновременно:
1. получать собственный органический трафик по узкому интенту;
2. усиливать несколько расширений;
3. переиспользовать общий движок и состояние документа;
4. давать релевантный путь в подходящее расширение;
5. не создавать каннибализацию между нашими URL.

Пример:

`resize image → /resize-image/ → пользователь меняет размер → получает файл → релевантный апселл Picture Converter`

Один движок может обслуживать много функций. Но SEO-входы должны оставаться узкими и понятными.

## 2. Главное правило SEO-архитектуры

**Один поисковый интент → один владелец URL.**

Не создавать широкую страницу, если она начинает конкурировать с уже существующим продуктом или точной страницей.

Пример: `/convert-image/` не создаётся автоматически. Сначала проверяются:
- Picture Converter;
- `/convert/`;
- exact-конвертеры `X-to-Y`;
- GSC;
- Semrush/ASO;
- SERP/Suggest;
- риск каннибализации.

## 3. Два параллельных трека

### Track A — привести текущий сайт в порядок

Цель: сделать уже опубликованный LayerPorter качественным, понятным, индексируемым и конверсионным до масштабирования.

Для каждой страницы проверяются:
- язык и естественность локализации;
- SEO: интент, семантика, Title, Description, H1, body, FAQ, перелинковка;
- AI-поиск: answer-first, фактическая полнота, структура, оригинальная полезность;
- CRO: первый экран, CTA, доверие, трение, релевантный маршрут в расширение;
- техника: canonical, hreflang, schema, robots, sitemap, www/non-www, региональные дубли;
- реальные данные: GSC + сохранённые Semrush/ASO + SERP/Suggest.

Статусы страниц:
- **READY** — можно индексировать, усиливать и масштабировать;
- **IMPROVE** — полезна и может жить, но требует улучшения;
- **HOLD** — не форсировать и не масштабировать до исправления.

### Track B — универсальные инструменты

Цель: строить общий функциональный слой, который одновременно создаёт SEO-точки входа и усиливает несколько расширений.

Принцип: **одно ядро → много узких функций → много узких SEO-входов → контекстный апселл в релевантное расширение**.

## 4. Обязательные три проверки до любой рекомендации или реализации

### Проверка 1 — фактическое состояние
- production;
- Git/master/ветки;
- текущий функционал;
- GSC;
- индексируемые URL;
- аналитика.

### Проверка 2 — реальный спрос
- GSC;
- Semrush;
- сохранённые ASO-исследования;
- Google SERP;
- Suggest;
- конкуренты;
- при необходимости GitHub/форумы/Reddit как источник гипотез, а не доказательство.

### Проверка 3 — качество
- естественность языка;
- соответствие поисковому интенту;
- соответствие реальной функции;
- CRO;
- отсутствие ложных обещаний;
- отсутствие каннибализации.

После трёх проверок формируется чек-лист. Только затем разрешены изменения.

## 5. CRO-модель

Коммерческая сверхцель сайта — **увеличивать установки релевантных расширений**, но не ценой ухудшения пользовательского сценария.

### Страница расширения

`Google → landing расширения → понял функцию → увидел реальный UX → Add to Chrome → Chrome Web Store → install → first success`

На такой странице установка — основной CTA.

### Страница универсального инструмента

`Google → узкий инструмент → пользователь получает результат → экспорт → контекстный апселл в релевантное расширение`

На такой странице нельзя требовать установку расширения до получения основной ценности, если это ухудшает решение поисковой задачи.

Правило: **нерелевантный CTA в расширение запрещён**. Для каждой страницы должна существовать карта:

`страница → интент → подходящее расширение → предложение → место CTA`.

Если подходящего расширения нет — CTA не подставляется искусственно.

## 6. AI-поиск

Не строить отдельный слой псевдо-оптимизации ради AI.

Для AI-поиска используем ту же качественную основу:
- прямой ответ в начале;
- факты и ограничения;
- реальная работающая функция;
- понятные H2/H3;
- FAQ из реальных вопросов;
- schema только когда соответствует содержанию;
- внутренняя перелинковка;
- оригинальная пользовательская ценность.

Никаких массовых AI-текстов ради количества URL.

## 7. Локализации

Новые массовые локали **заморожены до quality gate**.

Существующие локали не считаются одинаково качественными только потому, что опубликованы.

Для каждой локали до статуса READY обязательны:
1. реальное локальное написание запросов;
2. проверка сохранённой семантики ASO/Semrush;
3. естественная редакторская вычитка;
4. непрерывность ключевой семантики между Title / Description / H1 / body;
5. корректный hreflang/canonical;
6. CRO без машинных и неестественных формулировок.

## 8. Pareto-дорожная карта

### Sprint A0 — полный аудит текущего сайта — ACTIVE

Issue: #154.

**Результат:** единый реестр опубликованных страниц с классификацией READY / IMPROVE / HOLD и Pareto-приоритетом.

**Матрица:**
`URL | тип | язык | intent | ключ | источник | GSC | перевод | SEO | AI | CRO | расширение | CTA | техника | статус | приоритет | действие`

**Порядок проверки:**
1. URL, которые уже получают показы/клики GSC;
2. Home;
3. Extensions Hub;
4. Pinterest Downloader;
5. Picture Converter;
6. Convert Hub;
7. отдельные `/convert/X-to-Y/`;
8. Formats / Guides;
9. остальные опубликованные страницы.

В рамках аудита не делать массовых переписываний.

### Sprint A1 — технический контроль индекса — BLOCKED BY A0

Issue: #156.

**Результат:** единая корректная индексируемая структура после аудита.

Scope:
- www/non-www;
- canonical;
- hreflang;
- региональные дубли;
- sitemap;
- READY/HOLD policy;
- повторная отправка sitemap после исправления критических дефектов.

### Sprint A2 — денежные страницы

**Результат:** Home + Extensions Hub + Pinterest Downloader + Picture Converter доведены до согласованного уровня SEO / язык / CRO / AI / техника.

Основная метрика: переход в релевантное расширение и далее установка.

Приоритет внутри спринта определяется GSC и качественным аудитом, а не количеством локалей.

### Sprint A3 — страницы с уже подтверждённым поисковым спросом

**Результат:** Formats / Guides / отдельные converters переработаны по фактическим запросам GSC и SERP.

Правило: сначала URL с реальным сигналом Google, затем новые гипотезы.

### Sprint B0 — выбор общего функционального ядра

**Результат:** выбран минимальный общий runtime для изображений/документа без преждевременной сложной платформы.

Использовать существующую редакторскую дорожную карту как технический подслой.

### Sprint B1 — Crop + Resize

**Почему первым:** массовые запросы, простой общий код, высокая переиспользуемость, быстрый успешный экспорт.

Точки входа создаются только после исследования интентов.

### Sprint B2 — Compress + точные Convert-функции

**Почему:** общий pipeline обработки и экспорта, широкий спрос, связь с Picture Converter.

Не создавать один общий «converter» URL ради всех запросов.

### Sprint B3 — Text + Meme

**Почему:** переиспользует canvas/редактор, добавляет новые намерения без отдельного тяжёлого backend.

Meme Generator получает отдельный интент только после проверки спроса/выдачи.

### Sprint B4 — единая сессия + handoff из расширений

**Результат:** файл, полученный через расширение, можно открыть в общем ядре, выполнить дополнительные операции и экспортировать без повторного старта.

Picture Converter — первый кандидат. Pinterest Downloader — следующий.

### Sprint B5 — Media Core

Первый набор:
- Remove Sound / Mute Video;
- Extract Audio from Video.

**Почему:** один media runtime может обслуживать несколько будущих узких расширений и несколько SEO-функций.

До реализации обязательны benchmark производительности, лицензий, размера bundle и mobile memory.

### Sprint B6 — Background Removal benchmark

Не встраивать первое найденное решение.

Сначала сравнить:
- качество маски;
- волосы/мех/стекло/товары;
- скорость;
- стоимость;
- browser/server;
- лицензии;
- приватность;
- fallback.

Только победитель benchmark получает продуктовый спринт.

### Sprint B7 — AI-функции по подтверждённому спросу

Кандидаты:
- upscale;
- object removal;
- outpaint/extend.

Каждая функция проходит отдельный quality/cost/license gate и не блокирует базовый Editor Core.

## 9. Pareto-фильтр новой функции

Функция идёт выше в дорожной карте, если выполняется минимум 4 условия:
- есть подтверждённый поисковый или продуктовый спрос;
- переиспользует общее ядро;
- усиливает минимум одно расширение, желательно несколько;
- может дать отдельный узкий SEO-вход;
- закрывается коротким проверяемым спринтом;
- измеряется по успешному результату пользователя;
- не создаёт серьёзную лицензионную/стоимостную зависимость.

## 10. Что запрещено

- массово создавать локали до quality gate;
- переписывать хорошие страницы с нуля без доказанной причины;
- объединять разные интенты в одну SEO-страницу ради количества ключей;
- ставить нерелевантные CTA на расширения;
- обещать функции, которых продукт фактически не выполняет;
- мерджить старую `seo/LP-056-convert-copy-audit-49` вслепую: она разошлась с текущим production и используется только как источник материалов;
- форсировать индексацию HOLD-страниц;
- менять master напрямую.

## 11. Definition of Done спринта

Спринт считается завершённым только когда:
1. есть конкретный пользовательский результат;
2. проверки пройдены;
3. Git diff соответствует scope;
4. CI/build/smoke зелёные, если был код;
5. production проверен, если был deploy;
6. tracker обновлён;
7. следующий спринт разблокирован осознанно.

Статус VERIFIED ставится только после фактической проверки соответствующего результата.
