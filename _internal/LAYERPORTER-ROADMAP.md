## 1. Каноническая продуктовая модель

### Расширения

Расширение — **узкий продукт под один понятный поисковый интент**.

Примеры:
- Pinterest Downloader → скачать медиа с Pinterest;
- Picture Converter → скачать/конвертировать изображение;
- будущий Extract Audio from Video → извлечь аудио из видео.

Правило: не смешивать в позиционировании расширения десятки функций ради охвата. Основной запрос, обещание и первый пользовательский сценарий должны быть сфокусированы.

### Сайт

Сайт — **общая многофункциональная платформа LayerPorter** с переиспользуемым ядром.

Универсальные функции сайта должны одновременно:
1. получать собственный органический трафик по узкому интенту;
2. усиливать несколько расширений;
3. переиспользовать общий движок и состояние документа;
4. давать релевантный путь в подходящее расширение;
5. не создавать каннибализацию между нашими URL.

Пример:

`resize image → /resize-image/ → пользователь меняет размер → получает файл → релевантный апселл Picture Converter`

Один движок может обслуживать много функций. Но SEO-входы должны оставаться узкими и понятными.

### Общая инфраструктура и второй продуктовый сценарий

Первая аудитория — пользователи изображений/контента: узкие расширения и веб-инструменты. Вторая — владельцы сайтов и агентные клиенты: **аудит → исправленная страница → проверенный результат**. Общие операции и файлы переиспользуются; разные аудитории не получают искусственно одинаковый CTA.

Сайт — SEO-входы и рабочие интерфейсы. Расширения — узкие точки входа и контекстный переход к дополнительным функциям. MCP — операции для AI-клиентов; агент с готовыми профильными skills координирует аудит и изменения, браузер проверяет поведение. Не требуется четыре независимых SEO/CRO/AI/image продукта с дублирующим кодом.

Владелец сайта подключает репозиторий и выбирает страницу. Без репозитория вводит URL: система сначала определяет переносимость, затем выдаёт проверенную самостоятельную страницу либо preview/частичные исправления с конкретными недостающими доступами. Готовый результат включает страницу, а не только список советов.

Будущие платные функции — сложные задачи и экономия ручной работы: подготовка и применение изменений, пакетная обработка, фотосессии/мудборды и продвинутые визуальные операции. Монетизация и цена остаются гипотезой до измерения спроса, качества и стоимости результата.

## 2. Главное правило SEO-архитектуры

**Один поисковый интент → один владелец URL.**

Не создавать широкую страницу, если она начинает конкурировать с уже существующим продуктом или точной страницей.

Пример: `/convert-image/` не создаётся автоматически. Сначала проверяются:
- Picture Converter;
- `/convert/`;
- exact-конвертеры `X-to-Y`;
- GSC;
- Semrush/ASO;
- SERP/Suggest;
- риск каннибализации.

## 3. Два параллельных трека

### Track A — привести текущий сайт в порядок

Цель: сделать уже опубликованный LayerPorter качественным, понятным, индексируемым и конверсионным до масштабирования.

Для каждой страницы проверяются:
- язык и естественность локализации;
- SEO: интент, семантика, Title, Description, H1, body, FAQ, перелинковка;
- AI-поиск: answer-first, фактическая полнота, структура, оригинальная полезность;
- CRO: первый экран, CTA, доверие, трение, релевантный маршрут в расширение;
- техника: canonical, hreflang, schema, robots, sitemap, www/non-www, региональные дубли;
- реальные данные: GSC + сохранённые Semrush/ASO + SERP/Suggest.

Статусы страниц:
- **READY** — можно индексировать, усиливать и масштабировать;
- **IMPROVE** — полезна и может жить, но требует улучшения;
- **HOLD** — не форсировать и не масштабировать до исправления.

### Track B — универсальные инструменты

Цель: строить общий функциональный слой, который одновременно создаёт SEO-точки входа и усиливает несколько расширений.

Принцип: **одно ядро → много узких функций → много узких SEO-входов → контекстный апселл в релевантное расширение**.

## 4. Обязательные три проверки до любой рекомендации или реализации

### Проверка 1 — фактическое состояние
- production;
- Git/master/ветки;
- текущий функционал;
- GSC;
- индексируемые URL;
- аналитика.

### Проверка 2 — реальный спрос
- GSC;
- Semrush;
- сохранённые ASO-исследования;
- Google SERP;
- Suggest;
- конкуренты;
- при необходимости GitHub/форумы/Reddit как источник гипотез, а не доказательство.

### Проверка 3 — качество
- естественность языка;
- соответствие поисковому интенту;
- соответствие реальной функции;
- CRO;
- отсутствие ложных обещаний;
- отсутствие каннибализации.

Эти проверки выполняются в масштабе конкретной страницы/функции с переиспользованием существующих источников. Для исправления неверного лимита не требуется повторный аудит всего сайта или новое исследование рынка. Чек-лист фиксирует факты и релевантные риски своего изменения; отсутствие полного #154 не является общим блокером.

## 5. CRO-модель

Коммерческая сверхцель сайта — **увеличивать установки релевантных расширений**, но не ценой ухудшения пользовательского сценария.

### Страница расширения

`Google → landing расширения → понял функцию → увидел реальный UX → Add to Chrome → Chrome Web Store → install → first success`

На такой странице установка — основной CTA.

### Страница универсального инструмента

`Google → узкий инструмент → пользователь получает результат → экспорт → контекстный апселл в релевантное расширение`

На такой странице нельзя требовать установку расширения до получения основной ценности, если это ухудшает решение поисковой задачи.

Правило: **нерелевантный CTA в расширение запрещён**. Для каждой страницы должна существовать карта:

`страница → интент → подходящее расширение → предложение → место CTA`.

Если подходящего расширения нет — CTA не подставляется искусственно.

### Аудит и подготовка страницы

`URL / Git → аудит четырёх направлений → доказанные проблемы → подготовить улучшенную версию → сравнить → получить страницу/patch → разрешённое применение`.

Основное действие после аудита — «Подготовить улучшенную версию». Диагностика показывает факты и приоритеты; без данных не заявляет потерю продаж/трафика. Подробный SEO-разбор раскрывается ниже результата. Для MCP собственные метрики — успешное получение и применение результата, а не фиктивные установки расширения.

## 6. AI-поиск

Не строить отдельный слой псевдо-оптимизации ради AI.

Для AI-поиска используем ту же качественную основу:
- прямой ответ в начале;
- факты и ограничения;
- реальная работающая функция;
- понятные H2/H3;
- FAQ из реальных вопросов;
- schema только когда соответствует содержанию;
- внутренняя перелинковка;
- оригинальная пользовательская ценность.

Никаких массовых AI-текстов ради количества URL.

## 7. Локализации

Потенциал 52 локалей сохраняется как стратегия масштаба. Новые массовые локали **заморожены до quality gate**.

Существующие локали не считаются одинаково качественными только потому, что опубликованы.

Для каждой локали до статуса READY обязательны:
1. реальное локальное написание запросов;
2. проверка сохранённой семантики ASO/Semrush;
3. естественная редакторская вычитка;
4. непрерывность ключевой семантики между Title / Description / H1 / body;
5. корректный hreflang/canonical;
6. CRO без машинных и неестественных формулировок.

## 8. Pareto-дорожная карта — актуальный порядок

### Очередь и статусы на 2026-09-13

Это актуализация концепции и очереди, не новый полный аудит production. Исторические статусы ниже не подтверждают текущее состояние без проверки исполнителя.

| Поток | Ближайшее действие | После чего двигаться дальше |
| --- | --- | --- |
| Существующий сайт | Завершить незакрытый пользовательский дефект и текущий срез воронки; S1/S6 по факту актуального кода | Рабочий файл/сценарий, корректный CTA и индексационные настройки своего scope |

| MCP / улучшение страницы | **U1 сейчас: Git → единый аудит → исправленная страница → preview** | Проверены четыре направления аудита и поведение изменённой страницы |
| MCP без исходников | U2 после U1: URL → оценка переносимости → статическая версия или честный PARTIAL | Простой лендинг и сложная страница проходят разные корректные пути |
| Повторяемость / дистрибуция | U3: воспроизводимая установка, выдача результата; каталоги по готовому продукту | Чистый пользовательский запуск и рабочие ссылки установки |

| Сайт / расширение аудитора | U4 после проверенного агентного сценария | Выбран один интерфейс, подтверждены спрос, runtime и стоимость |
| Локали / сложные функции | Небольшие проверенные партии / отдельные гипотезы | Свой quality gate, без ожидания всех будущих инструментов |

Потоки сайта и MCP могут идти в существующих разных чатах владельца; один шаблон/файл не отдавать конкурирующим исполнителям. Самостоятельные отправки задач запрещены: карточки передаются владельцу. Календарные сроки назначаются исполнителем после короткой сверки кода; порядок выше определяется результатом, а не количеством дней.

### Ближайший результат: существующие конвертеры и воронка — #181

Девять существующих /convert/[slug]/: webp-to-jpg, jpg-to-pdf, pdf-to-jpg, png-to-psd, jpg-to-psd, psd-to-png, psd-to-jpg, favicon-generator, canva-to-google-slides. Последний — checker перед ручным переносом PPTX, не автоматический конвертер.

Для каждого: URL → intent → реальная функция/лимиты → extension или NO EXTENSION → offer → placement → event. Сначала результат и экспорт, затем подходящий CTA. Использовать существующий layout и runtime.

**Уже сообщено в #181:** PT-BR 9/9, RU JPG→PDF и RU PNG→PSD — DEPLOY SUCCESS. Не реализовывать повторно. RU PNG→PSD ещё требует live-проверки по последнему комментарию. Следующий кандидат RU WebP→JPG проверяется против актуального master и сохранённой семантики.

### Локализации: следующий проверенный exact URL

Использовать сохранённые SEO-базы, Wordstat/Semrush/ASO/GSC; не начинать исследование 52 рынков заново. После рабочего пилота выпускать небольшими партиями. Выполненные страницы сохранять; не переписывать ради единообразия.

Массовое расширение остаётся под quality gate. Оно не запрещает выпуск одной качественной страницы и не требует ждать всех локалей.

**Уже в работе:** [PR #251](https://github.com/OlegStrateg/layerporter-site/pull/251), ветка feat/LP-098-image-resize-crop-tools. Код страниц и browser core добавлен; следующий шаг — приёмка, не повторная реализация. CI-статус и ограничения проверки — в разделе 13.

### MCP — опубликованное ядро и следующий единый аудит

@layerporter/image-optimizer-mcp@0.1.0 опубликован из принятого SHA 8ca11132b8cec267d1b88ff85232d58483353c63. Чистая установка публичного пакета по имени → официальный MCP-клиент → resource → реальный декодированный файл проверены. Доказательства: [отчёт приёмки и внешнего smoke](PR-222-INTEGRATION-REVIEW-0f023b6.md). Публикация в Official MCP Registry не выполнена.

Следующая продуктовая линия — **«Аудит → исправленная страница»**. Все четыре направления входят сразу: SEO, видимость в ИИ-поиске, CRO и изображения. Исправления охватывают выбранные подтверждённые проблемы; наиболее готовая автоматическая операция — обработка изображений.

**U1 — рекомендуемое следующее задание:** подключённый Git и одна страница LayerPorter → общий отчёт → выбранные изменения исходников → сборка → preview до/после → проверка основного пути → готовый patch. Это пилот на существующем MCP с агентом, а не новый универсальный hosted сервис. PR готовится в рамках разрешений исполнителя; merge/deploy отдельно.

**U2 — без репозитория:** сначала определить доступные ресурсы, интерактивность и внешние зависимости. Простой лендинг можно реконструировать в самостоятельную страницу. Если недоступен backend, авторизация или реальная обработка, выдавать preview/частичный результат и запрос конкретных исходников/CMS. Не выдавать похожую картинку за рабочую замену.

**U3 → U4:** воспроизводимый сценарий и выдача файлов → затем выбранный веб-интерфейс или расширение. Один сбор фактов и формат findings/changes/evidence переиспользуются; skills и MCP не заменяют друг друга. Публичное исполнение URL требует своей оценки runtime, лимитов, стоимости и хранения.

Рекомендуемые готовые источники: AgriciDaniel seo-images; Lawrence Hitches / StudioHawk technical-seo-audit; Corey Haines CRO/AI-SEO; Microsoft playwright-cli для проверки. clone-website — только источник метода реконструкции, после лицензии и адаптации. Не переносить неподходящий Next.js scaffold, массовый веер агентов и автоматический merge.

Обязательное правило проверки: записать сценарии оригинала ДО изменений и повторить ПОСЛЕ; desktop/mobile, сеть/ресурсы, кнопки/формы и настоящий результат. Внешне похожая страница с неподтверждёнными функциями — PREVIEW ONLY/PARTIAL. Готовность на localhost не доказывает внешние интеграции будущего домена.

[Полная концепция, матрица входов, этапы и приёмка](IMAGE-AUDIT-FIRST-2026-09-13.md). Статус этой линии — **PRODUCT DECISION / NOT IMPLEMENTED**. Проверка одной страницы не называется полным обходом сайта. AI-видимость без наблюдения выдачи и CRO без аналитики — оценки и гипотезы. Уменьшение байтов не равно улучшению LCP или продаж.

### A0 #154 и A1 #156 — фоновый аудит и узкие технические исправления

A0 даёт полный реестр READY/IMPROVE/HOLD. Текущий аудит выборочный, не объявляется завершённым A0.

Подтверждённый дефект canonical/host/hreflang/sitemap конкретной партии можно исправлять после проверки этого scope. **A1 больше не заблокирован целиком ожиданием A0.** Старое описание #156 необходимо читать вместе с более свежим приоритетом #153 и этим уточнением. Массовая миграция URL требует собственной карты последствий.

### Последующая продуктовая линия

- Shared handoff из расширений после полезных веб-функций; V1 не обязан быть бесшовным.
- Background removal/upscale/object removal/inpainting — после quality/cost/license benchmark.
- Canva/Figma/Photoshop: сначала фактические функции и конкретный сценарий; не путать PSD-контейнер, перенос родных слоёв и AI-реконструкцию. Canva — предпочтительная гипотеза владельца для следующего исследования, не доказанный объём спроса. Межформатный перенос и дорисовка фона под слоями проходят отдельный benchmark.
- Reader из TLDR — исследовательская гипотеза, а не подтверждённая свободная ниша.
- Платные фотосессии/мудборды — следующий слой после устойчивого бесплатного пути.
- Отдельный продукт сбора CRO/heatmap — HOLD как отдельная аудитория. Экспертный CRO-разбор страницы входит в единый MCP/агентный аудит сейчас.

### Правило остановки

Один выпуск = один полезный, проверенный пользовательский результат. После его DoD перейти к следующему пункту. Блокирует конкретный релиз основной функциональный дефект, ложное обещание или серьёзный риск своего scope; не блокирует отсутствие будущих инструментов и незавершённая полировка других страниц.

## 9. Pareto-фильтр новой функции

Функция идёт выше в дорожной карте, если выполняется минимум 4 условия:
- есть подтверждённый поисковый или продуктовый спрос;
- переиспользует общее ядро;
- усиливает минимум одно расширение, желательно несколько;
- может дать отдельный узкий SEO-вход;
- закрывается коротким проверяемым спринтом;
- измеряется по успешному результату пользователя;
- не создаёт серьёзную лицензионную/стоимостную зависимость.

## 10. Что запрещено

- массово создавать локали до quality gate;
- переписывать хорошие страницы с нуля без доказанной причины;
- объединять разные интенты в одну SEO-страницу ради количества ключей;
- ставить нерелевантные CTA на расширения;
- обещать функции, которых продукт фактически не выполняет;
- мерджить старую `seo/LP-056-convert-copy-audit-49` вслепую: она разошлась с текущим production и используется только как источник материалов;
- форсировать индексацию HOLD-страниц;
- менять master напрямую.

## 11. Definition of Done спринта

Спринт считается завершённым только когда:
1. есть конкретный пользовательский результат;
2. проверки пройдены;
3. Git diff соответствует scope;
4. CI/build/smoke зелёные, если был код;
5. production проверен, если был deploy;
6. tracker обновлён;
7. следующий спринт разблокирован осознанно.

Статус VERIFIED ставится только после фактической проверки соответствующего результата.

Для подготовки страницы дополнительно: исходный и повторный сценарии записаны; выбранные изменения связаны с находками; реальные ресурсы доступны; функциональные зависимости проверены или явно перечислены; у patch есть точная база и способ отката. PREVIEW ONLY, VERIFIED IN PREVIEW и DEPLOYED VERIFIED не смешиваются.

### 13.3 Принятые принципы из материала

**Продвигаем задачу и реальный результат:** обнаружить тяжёлые изображения, подготовить responsive assets, исправить выбранную страницу. Формулировки «весь сайт», «исправляет LCP», «без потери качества» допустимы только при соответствующей функции и доказательстве.

Воронка: **поиск проблемы → полезный аудит → доказанная находка → install/connect → первое проверенное исправление → повторная сессия → рекомендация/распространение результата**. Где возможно по стоимости и доступам, первый ограниченный публичный аудит — до регистрации. Доступ к Git и приватным данным требует соответствующей авторизации.

Короткий верх README/landing: что получится, рабочий путь установки, реальный пример, ограничения и поддержка. Demo 30–45 секунд — кандидат формата, не обязательный дорогой видеопроект. Prompt gallery начинать с нескольких реально пройденных задач; tool names/descriptions/schemas должны точно описывать выполняемое действие.

Компактная поверхность MCP, краткий summary и подробности по запросу; бинарники через Resources. Не менять существующие семь tools ради предложенных в исходнике названий и не вводить универсальный execute/shell.

Единая проверяемая identity/metadata: существующее имя `@layerporter/image-optimizer-mcp`, версия, transport, реальные возможности, install, homepage, support, data flow. Не переименовывать в примерное `@layerporter/mcp`. Генерировать только поддерживаемые целевыми схемами файлы; metadata не должна обещать отсутствующие Remote/OAuth/MCPB.

Trust: фактическая матрица операций/доступов, публичный support route, SECURITY/PRIVACY, release history, integrity и результаты проверок. Закрытый сайт-репозиторий не открывать ради каталога; отдельный публичный adapter/export требует решения владельца. Не объявлять отсутствие filesystem/shell во всей агентной цепочке, если Git/build-агент ими пользуется.

SEO-порядок: проблема → сценарий/клиент → технический MCP-интент. Новые страницы только с полезной функцией и без конкуренции существующим /convert/ и /tools/. Markdown docs и llms.txt — удобство чтения, не доказанный рост AI-цитирования.

### 13.4 Каналы и установки: что подтверждено, что условно

- [Official Registry](https://modelcontextprotocol.io/registry/about) — metadata/discovery feed, поддерживает публично доступный способ установки; listing не доказывает трафик, безопасность или совместимость. Read-back проверяет точную identity/version.
- [Smithery](https://smithery.ai/docs/build/publish) — опубликованы пути Remote Streamable HTTP и local MCPB. Static server card предусмотрен при невозможности автоматического scan. Простой npm listing не заменяет эти prerequisites. 401 для неаутентифицированного запроса и 403 при недостаточных правах не смешивать.
- [Glama](https://glama.ai/mcp/faq) — GitHub/open-source submission и remote connector имеют разные требования. glama.json — специфичная metadata, не универсальный стандарт; совместимость приватного monorepo с выбранным путём сначала подтвердить.
- [MCPB](https://github.com/modelcontextprotocol/mcpb) — кандидат удобной локальной доставки. Для нашего native Sharp/libvips сначала реальная матрица OS/arch/client. Не объявлять основным способом до прохождения установки и обработки изображения.
- [mcp-submit](https://github.com/jordanlyall/mcp-submit) существует; README различает API/CLI, создание issue/PR и открытие ручной формы. Это не «все каталоги опубликованы одной командой». Сначала ревью зависимостей/доступов и dry-run; запуск submission, сообщения и PR — только в разрешённом scope. В этой задаче не запускался.
- Install UX по #249: сначала проверенные Claude Code, Cursor, VS Code; остальные только после точного smoke. Предложить выбор клиента явно — OS/browser не доказывают, какой AI-клиент установлен.
- Remote + OAuth — рекомендуемое направление для массового подключения после проверки, не готовая замена stdio и не условие любого релиза. Требования новой спецификации/SDK из #252 остаются на архитектурном ревью; текущую 0.1.0 не переписывать ради протокольной моды.

### 13.5 Growth, аналитика и ограничения

Главная метрика — завершённые проверенные workflow, затем first-success rate и повторная сессия/7d active. Дополнительно — ошибки по этапам, время до результата, P50/P95, стоимость успешной задачи и число вызовов на результат. Downloads/stars/listings — вспомогательные сигналы, не уникальные установки или активные пользователи.

Атрибуция: источник → landing → install/connect → первый результат → второй результат. События чужих каталогов и локального клиента не считать наблюдаемыми без источника данных/согласованной телеметрии. Не передавать содержимое страниц, приватные пути и изображения ради маркетинговой аналитики.

Freemium — гипотеза законченной ограниченной задачи, а не произвольных N tool calls. Число бесплатных аудитов/изображений и цена определяются себестоимостью; не копировать 3/10/20 из примеров как утверждённый тариф.

Демо, реальные before/after и технический разбор → подходящие сообщества, release notes, newsletter и вторичные каталоги. Подготовить материалы можно до публикационного разрешения; отправки/посты остаются отдельными действиями владельца. Не накручивать stars/downloads, не создавать фиктивные issues и не спамить одинаковым постом.

Shareable reports — после подтверждения пользы; сначала локальный/скачиваемый отчёт. Публичное размещение по явному выбору пользователя, с удалением приватных данных и контролем доступа/срока. Не превращать отчёты автоматически в индексируемые страницы. SDK, GitHub Action, интеграции Figma/Chrome, мониторинг и массовые benchmarks — последующие ставки по реальному повторному использованию, не prerequisites первого результата.

Новые security scanners/Inspector не добавлять ради бейджа. #246 уже создаёт независимый Inspector gate; #248 обоснованно оставляет mcp-scan условным до проверки внешнего обмена данными. Scan PASS не гарантирует безопасность. Подписи/provenance указывать только при фактической проверке; действующий deploy control plane не дублировать.

Первое действие исполнителя — понять, исполняются ли steps. Если GitHub runner не запускается, выполнить эквивалентный проверяемый прогон в доступной чистой среде с SHA/версиями/logs/artifacts, не ослабляя проверки. Это даёт evidence, но не подменяет обязательный статус CI, если его требует интеграция. Причину недоступности runner устранить отдельно; повторные пустые rerun не являются прогрессом.

Приёмка: exact public package/source equivalence, независимый Inspector, protocol→resource→реальный декодированный файл, результат dependency audit.

### P2 — согласованный выпуск и установка

Принять #248, проверить SECURITY/PRIVACY и доступность публичного support route вне приватного GitHub. Если изменения должны попасть в npm, подготовить один минимальный новый patch-release без изменения алгоритмов: version/name/server identity согласованы, точная версия ещё свободна, публикация отдельно разрешена. 0.1.0 не переписывать. Новый кандидат проходит свой tarball/release gate; после публикации проверяется извне.

По #249 довести Claude Code → Cursor → VS Code: конкретный клиент/OS/версия пакета, чистая установка, реальный результат и повторная сессия. По мере PASS показывать готовые install-кнопки/инструкции; остальные клиенты явно pending. Хотя бы один доказанный путь позволяет начать целевую дистрибуцию, полное покрытие этой фазы означает три проверенных клиента.

### P3 — видимость и первый пользовательский результат

Official Registry: согласованные metadata, ownership, разрешённая публикация → read-back точного имени/версии → проверка установки по публичной записи. Это отдельный результат от npm publish.

Product/docs/README: согласованная фактическая capability, короткая установка, несколько работающих prompts, реальный before/after, поддержка и privacy. Убрать candidate/unpublished только там, где статус действительно изменился. Без обещаний full audit, Remote/OAuth или универсальной совместимости.

Подготовить и разместить после разрешения 2–3 подходящие вторичные карточки/заявки, учитывая требования. Для каждой: eligibility → submission → accepted/live → переход → install → first success; отправленная заявка не равна размещению. Smithery ждёт проверенного Remote или MCPB, не блокирует Registry. Glama проверяется с учётом приватности текущего monorepo; не открывать весь репозиторий ради каталога.

Настроить доступную атрибуцию install clicks и успешного результата без скрытой телеметрии. Подготовить одно реальное demo и технический launch-текст; не строить маркетинговую платформу. Отправки в сообщества — отдельное разрешённое действие.

### P4 — расширение доступа через Remote

После устойчивого local path продолжить #252: фактический ограниченный Remote R0 → проверка transport/клиентов/артефактов/лимитов → затем R1 OAuth и защищённые действия по подтверждённой необходимости. Это отдельный технический релиз, а не настройка карточки каталога.

MCPB — отдельная проверка native Sharp на целевых OS/arch. Наличие HTTP endpoint или npm не означает, что доступ открывается во всех клиентах/галереях; требования конкретного клиента и review проверяются перед заявлением о поддержке. Срок рассмотрения внешнего каталога не контролируется LayerPorter.

### Когда считаем цикл завершённым

**Публикация текущего MCP завершена:** package gate PASS; публичная установка и выдача результата проверены; trust/docs соответствуют версии; Official Registry запись читается и ведёт к работающей установке; для заявленных клиентов есть evidence; demo и install path доступны; результаты первых целевых размещений записаны, pending review не маскируется.

**Расширенный доступ завершён:** дополнительно Remote/OAuth действительно работает в заявленных клиентах, выдаёт файлы, проходит негативные проверки доступа и имеет понятные лимиты/стоимость. MCPB считается готовым только по собственной матрице. «Видимость» означает доступность и проверяемое обнаружение в выбранных каналах, не гарантированные позиции или рекомендации всех AI-систем.

Оценка планирования: P1–P3 — короткий release-цикл, целевой ориентир 2–3 рабочих дня при доступной среде, аккаунтах и отсутствии нового дефекта; внешняя модерация вне этой оценки. Это ориентир, не обещанная дата или выполненный запуск. P4 оценивается отдельно после runnable prototype и выбора провайдера; не давать дату по одному архитектурному документу. Исполнитель после первого прогона уточняет остаток по фактическим препятствиям.
